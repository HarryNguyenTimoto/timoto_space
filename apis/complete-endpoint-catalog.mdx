# Complete Endpoint and Flow Catalog

This is the source-grounded implementation specification for the seven TiMoto project roots. It is intentionally operational: each feature is described as a stateful flow, each HTTP family is classified by ownership and authentication, and each route is mapped to its expected clean response, failure class, and side effect.

<Note>
  This catalog is derived from the checked-out Django URL modules, React clients, Lambda/control-plane code, Terraform, and existing Postman references. It is not a claim that every route is deployed on every environment. Treat a route as live only after a same-environment request succeeds with a current base URL, credentials, and correlation ID.
</Note>

## 1. System inventory and ownership

| Project root | Product surface | Primary responsibility | Durable state or external dependency |
| --- | --- | --- | --- |
| timoto-mobile | Rider mobile app and rider API | Vehicle intake, OCR, evaluation, pricing, pickup, listing | Django models, object storage, JWT, notification providers |
| timoto-internal-app | OPS web application and operator API | Review queue, fair-market-price decisions, pickup, purchase and payout operations | Django models, bank/payout callbacks, HMAC webhooks |
| timoto-dealer-portal | Dealer portal and dealer API | Auctions, catalog, checkout, deposits, full payment, delivery | Django/SQL, VietQR, VNPay, dealer permissions |
| timoto_dealer_portal_v2 | Dealer-facing v2 client | Alternate dealer UI and API client contracts | Verify target backend and route compatibility before changing |
| TiMoto-AI-Web | Public marketing/waitlist web | Landing page, Android waitlist UX, product education | Browser state; waitlist Lambda exists separately and is not proven wired to the form |
| chototcaodulieu | Market-data collection | Chotot listing/detail collection, image sync, quality filtering | DynamoDB, S3 CSV, SQS image worker |
| AI_infra_timoto | AI repair/control plane | Sanitized incident intake, exact-target repair plans, isolated verification, signed artifacts, draft PR | S3/DynamoDB/Terraform/ECS metadata; control plane in ap-southeast-1 |

The six application/data repositories are not one service. The seventh root, AI_infra_timoto, is a control plane with an approval boundary. It must not be described as an automatic production deployer.

## 2. Canonical lifecycle flows

### 2.1 Rider sell flow

1. A rider registers or logs in through mobile auth.
2. The app captures vehicle registration and photos.
3. OCR extracts registration fields. The rider reviews and corrects fields.
4. The app uploads images, video, audio, and recognition paper through upload endpoints. Presigned URLs are transport-only credentials and must not be logged.
5. A bike submission is created and moves to an evaluation state.
6. The evaluation service collects exterior, engine, price, and full-evaluation answers.
7. A price-selection operation records the rider's selected path: instant sale, marketplace listing, or operator review.
8. For instant sale, the rider confirms the listing; the operator later confirms or rejects the payout.
9. For marketplace sale, the rider confirms the listing; the listing becomes visible only after server-side validation.
10. Pickup is requested. Operations assigns an owner, inspects the vehicle, and records pickup completion.
11. The system records sale history and feedback. Every transition must be idempotent for retries.

### 2.2 Operator fair-market-price flow

1. The internal app authenticates staff and loads the valuation queue.
2. An operator opens a submission and reads the normalized bike facts plus AI review choice/report.
3. The operator enters a price, rationale, and optional corrections.
4. The submit endpoint validates the bike state, computes snapshot rates, resolves the SLA tracker, and emits the configured HMAC webhook.
5. A clean response returns the persisted decision and correlation identifiers. A duplicate submission returns conflict semantics, not a second payout.
6. The rejection path records a reason and exposes the next action to the rider or dealer.
7. Webhook delivery is retried by the receiver using the event idempotency key.

### 2.3 Dealer auction and purchase flow

1. Dealer authenticates through the dealer portal.
2. Dealer reads catalog and auction inventory, applying server-side filters.
3. Dealer creates or joins an auction/order intent.
4. Deposit is created. The API returns a checkout/payment reference; it must not claim money is received yet.
5. VietQR or VNPay callback is verified independently from the browser redirect.
6. The payment state changes only after signature and amount/order checks succeed.
7. Full payment, delivery, notary, and remaining-payment steps advance the order state.
8. A clean order response exposes the state machine; invalid transitions return conflict.
9. Notification/device routes inform the dealer, but notifications are not the source of truth for payment.

### 2.4 Public web waitlist flow

1. The browser validates name, email, and phone format locally.
2. The current landing form shows a success alert and clears state; source review found no network call from that form.
3. The separate waitlist Lambda contract in docs-kb accepts a server-side request when wired by a deployment.
4. Until a live request is observed, document the form as UX-only and do not promise persistence.

### 2.5 Chotot market-data flow

1. The daily collector requests Chotot v1 listing pages with the motorcycle category.
2. Listing records are normalized and deduplicated into DynamoDB table chotot-xe-may.
3. Detail calls enrich a listing and apply quality filters.
4. Images are queued through SQS and copied by the worker; image failure must not erase the listing record.
5. A weekly refresh checkpoint controls completeness. CSV exports are written to S3.
6. No Aurora write was proven in the checked-out source; consumers must treat this dataset as market intelligence, not transaction inventory.

### 2.6 AI repair flow

1. An incident is accepted only for one of the six exact target applications.
2. Intake is sanitized; stack traces, URLs, and credentials are redacted before persistence.
3. The control plane binds the repair request to a source SHA and immutable target metadata.
4. A plan is generated for a narrow change. The isolated runner executes tests in a disposable environment.
5. The artifact is signed and attached to a draft pull request.
6. A human reviews and merges. Production deployment remains a separate approval.
7. Any request outside the allow-list is rejected with a safe error and no repository mutation.

## 3. Response taxonomy

### 3.1 Clean response classes

| Class | Meaning | Required shape or rule |
| --- | --- | --- |
| 200 object | Read or successful mutation | JSON object from the view/serializer; preserve stable field names |
| 200 list | Collection read | Prefer count, next, previous, results when the endpoint uses DRF pagination; otherwise document the actual list shape |
| 201 created | New resource | Return identifier and canonical state; do not imply downstream payment or pickup completion |
| 202 accepted | Asynchronous work | Return job/event identifier and polling or callback expectation |
| 204 empty | Successful delete/logout/ack | Body must be empty; clients must not parse JSON |
| 302 redirect | Browser payment return | Redirect is not payment confirmation; verify callback/IPN separately |
| Binary | PDF or media download | Correct Content-Type, Content-Disposition, and bounded size |
| Webhook ack | S2S callback | Fast 2xx acknowledgement after signature and idempotency checks; process asynchronously when possible |

No global envelope was proven across all seven roots. Some endpoints return serializer objects, some return DRF validation dictionaries, some return message/status objects, and some return redirects or files. Client code must branch on status and content type rather than assuming one envelope.

### 3.2 Error classes

| Status | Classification | Client behavior |
| --- | --- | --- |
| 400 | Malformed request or business validation | Show field-level errors; do not retry unchanged payload |
| 401 | Missing, expired, or invalid JWT/HMAC | Refresh token once where supported; otherwise sign in again |
| 403 | Authenticated but not allowed by role/ownership | Stop retrying; show permission state |
| 404 | Resource or route not found | Distinguish missing object from wrong base URL; log route fingerprint |
| 409 | State conflict, duplicate idempotency key, already paid, already submitted | Re-read canonical state and reconcile |
| 413 | Upload too large | Reduce media or use supported presigned upload |
| 415 | Unsupported media type | Correct Content-Type and file type |
| 422 | Semantic validation if emitted by a gateway/client | Display field errors; do not blindly retry |
| 429 | Rate limit | Honor Retry-After and exponential backoff |
| 500 | Unhandled application error | Retry only idempotent reads; attach correlation ID |
| 502 | Upstream provider failure | Retry with bounded backoff; preserve pending state |
| 503 | Maintenance or unavailable dependency | Surface degraded state; do not create duplicate order/payment |
| 504 | Upstream timeout | Poll/reconcile before issuing a second command |

Error bodies must be safe to expose. They may include a machine code, human detail, field map, correlation ID, and retryable flag. They must not include access tokens, HMAC secrets, presigned URLs after their useful lifetime, raw SQL, or provider credentials.

## 4. Authentication and trust boundaries

| Boundary | Credential | Verification |
| --- | --- | --- |
| Mobile rider | JWT access/refresh tokens | User identity, token expiry, ownership checks |
| Internal OPS | Staff JWT/session and role | Staff role plus object-level permission |
| Dealer | Dealer JWT/session | Dealer account, dealership, order ownership |
| Browser payment return | Redirect query | Informational only; never final payment proof |
| VietQR/VNPay callback | Provider signature plus amount/order checks | Idempotent callback processing |
| Internal webhooks | HMAC with timestamp, nonce, and event id | Reject stale timestamp, bad signature, duplicate event |
| AI repair intake | Signed internal request and allow-listed target | Sanitization, source SHA binding, human approval |
| Chotot collection | Upstream HTTP client | Respect source terms, rate limits, and data retention policy |

## 9. Cross-project response and idempotency rules

1. Every mutation accepts or generates an idempotency key. For payment and webhook commands, the key must be persisted before side effects.
2. A retry after timeout must first read the canonical resource state.
3. A 409 must include the current state or a URL to retrieve it where the source serializer allows.
4. Browser redirects, push notifications, and UI alerts are hints, not durable truth.
5. Payment callbacks must compare provider transaction id, local order id, amount, currency, and signature before marking paid.
6. HMAC requests must bind method, path, timestamp, nonce, body hash, and key id. Reject stale timestamps and duplicate nonces.
7. Paginated list endpoints must document ordering and cursor/page semantics. The absence of pagination metadata is a contract gap, not permission to infer it.
8. Error logs must include correlation id, route fingerprint, status, retryability, and source project, but never tokens or raw payment payloads.
9. A clean response must be stable across retries. If a command is asynchronous, return an operation id instead of pretending the final state is complete.
10. A compatibility alias may share implementation, but it must be listed as an alias so clients can migrate deliberately.

## 11. Minimum contract-test matrix

For every mutating endpoint, test:

- valid request returns documented success status and content type;
- missing authentication returns 401;
- authenticated wrong role returns 403;
- malformed body returns 400 with safe field errors;
- unknown identifier returns 404;
- duplicate command or invalid state returns 409;
- provider timeout does not create a duplicate resource;
- retry with the same idempotency key returns the same canonical result;
- logs contain a correlation id and redact secrets.

For every webhook, additionally test:

- bad signature;
- stale timestamp;
- duplicate event id;
- amount/order mismatch;
- valid callback replay;
- callback before local checkout row exists;
- provider retry after a 5xx.
