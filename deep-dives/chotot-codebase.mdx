# Deep Dive: chototcaodulieu Codebase

## Scope and operating model

Root: /Users/toannguyen/chototcaodulieu. This repository is a collection of scraping, backfill, image synchronization, export, dashboard and AWS deployment tools, rather than one small service. The canonical daily Lambda flow is described in chotot.py; other scripts are one-time/historical snapshots and must not be conflated with the scheduled path. AGENT_HANDOFF.md identifies DynamoDB chotot-xe-may, image sync state table, S3 bucket, queue/DLQ and EventBridge schedules. Validate these against current AWS before operational changes.

## Daily listing pipeline

chotot.py defines Chotot v1 public listing endpoint and v2 detail endpoint, request session/retry adapter, Vietnam-local day bounds and category parameters. scrape_day:

1. computes local target day epoch range;
2. paginates listing calls and extracts list IDs;
3. fetches details concurrently;
4. accumulates raw source records;
5. upserts DynamoDB by list_id. The request layer must handle non-200, malformed JSON, throttling and transient network failures. Request retry count, headers and timeouts live in \_make_session/\_fetch_listing_page/\_fetch_detail_one. Listing pages and detail records have different completeness. A listing record without detail should be represented as partial/failed enrichment, not silently treated as a full vehicle row.

upsert_to_dynamodb uses the low-level DynamoDB client and TypeSerializer to write batches. The table key is list_id and raw JSON is retained. BatchWriteItem can return unprocessed items; successful invocation alone does not prove every row stored. Capture accepted, rejected, unprocessed counts and checkpoint only after retry strategy succeeds.

## Weekly refresh

refresh_handler.py scans list_id keys using LastEvaluatedKey, reads an S3 JSON checkpoint, invokes v2 detail fetches in bounded batches and upserts successful detail rows. It tracks run_id, processed/refreshed/errors/status and last_evaluated_key. A time budget triggers checkpoint save and asynchronous self-invocation. dry_run suppresses writes/checkpoint. reset begins a new run. Operationally:

- checkpoint version/schema should be validated before continuing;
- concurrent refresh runs need a single-writer/lease policy;
- an item with failed detail fetch stays eligible for another pass;
- completion means scan finished, not every detail fetched successfully;
- reset is a stateful destructive semantic and should be used deliberately.

## Images and S3

Image pipeline uses a producer and SQS queue to schedule records; a worker downloads and writes images to S3. AGENT_HANDOFF lists queue chotot-image-sync-queue and DLQ chotot-image-sync-dlq. monitor_image_sync.py polls queue stats and summarizes state table/S3 counts. Message contracts should include list_id, source URLs, image type/order and attempt metadata. Worker response is message delete after successful processing, visibility retry on transient errors, DLQ after configured redrive. Ensure content-type, size limits, URL validation, checksum/key determinism and S3 ACL policy. Public URLs/CloudFront delivery have separate cache invalidation behavior.

## Export and dashboard flows

CSV/JSONL/export scripts normalize source attributes, map original image URLs to S3 keys, combine snapshot and recent DynamoDB rows, generate metadata/sample files and upload to S3. Some scripts contain machine-local Downloads paths; these are operator utilities and should not run unreviewed in scheduled Lambda. Export correctness includes row counts, duplicate IDs, schema version, timestamps and source watermark. A CDN invalidation is an external write and should only occur after successful upload. Dashboard API and static frontend are distinct from the ingestion source.

## Data model and quality

Raw Chotot ad shape is nested under ad and can evolve upstream. Keep raw payload plus normalized fields so parser failures are recoverable. Track first_seen, last_seen, source listing timestamp, detail-fetch timestamp, scrape run id, image status, quality rejection reason and source URL. Filtering should preserve reason codes rather than dropping all evidence. Prices are VND and should be parsed to integer with null/invalid distinction. Time is Vietnam local for collection windows and UTC for storage/event timestamps; avoid naive local timestamps.

## Failure taxonomy

- upstream listing 429/5xx: bounded exponential retry, then run-level failure/checkpoint;
- detail 404/removed: mark unavailable/removed and retain history;
- malformed item: quarantine by list_id and continue batch;
- DynamoDB throttling/unprocessed write: retry only those items;
- S3 put failure: retain queue message for retry;
- poison image URL/message: fail safely and DLQ;
- refresh timeout: persist cursor before self-chain;
- export upload failure: preserve previous output and do not invalidate CDN;
- checkpoint parse/schema error: halt rather than reset silently.

## Security, privacy and terms

Scraping source traffic should be rate limited and aligned with source terms. Never publish raw user/seller personal information from ads without policy basis. Restrict S3/DynamoDB IAM by required prefix/table; avoid credentials in scripts. Downloaders must defend against arbitrary URL/SSRF by allowlisting Chotot image hosts, enforcing HTTPS, blocking private IP ranges and bounding redirects/timeouts. Logs should use listing IDs and counters, not full raw ad objects.

## Observability and reconciliation

Each run needs run_id, target date/range, requested/listed/detail-success/detail-failure/upsert/export counts, retry count, checkpoint key and elapsed time. Reconcile listing IDs in source pages with DynamoDB unique key count; verify samples against raw detail; count images expected/downloaded/DLQ; check latest checkpoint; compare export count/hash to database snapshot. Separate "run completed", "data complete", "export uploaded" and "CDN current" states.

## Acceptance scenarios

Test duplicate listing ingestion, changed detail payload, absent detail, invalid JSON, 429/5xx retries, partial DynamoDB batch, checkpoint resume, dry run, reset, time-budget self-chain, concurrent worker behavior, SQS duplicate delivery, poison image, DLQ, export duplicate suppression, upload failure and CDN invalidation ordering. Fixture tests should avoid live Chotot/AWS calls by default and record which smoke tests are live.

## Daily scraper record contract

chotot.py uses v1 /public/ad-listing for IDs and v2 /public/ad-listing/:list_id for detailed raw payload. It computes Vietnam day boundaries and fetches details through a shared requests.Session with retry adapter. Keep event time (source list_time), collection time (scraped_at) and detail refresh time separate. The natural identity is source list_id. Upsert should be repeatable: same listing/day does not add duplicate rows, later detail can update its raw payload.

Represent stages explicitly: discovered, detail_fetched, normalized, quality_passed/failed, persisted. If detail fetch fails, do not call the listing fully enriched. If an ad disappears upstream, do not delete historic row unless retention policy requires it. Stable failure reason codes support replay and quality reporting.

## Image synchronization protocol

Producer and worker are separate programs/Lambdas. Each SQS record must be independently idempotent so redelivery cannot create duplicate logical media. Deterministic S3 keys should include list ID, media role/index and source hash or equivalent. Enforce URL host allowlist, HTTPS, private-network rejection, maximum redirects, content length/type and download timeout before writing. Store expected/complete/failed image counts with status table. Queue depth alone does not say whether images are complete; compare source count, completed count, retry count and DLQ.

Monitor_image_sync.py reports queue and state metrics at different cadences: queue polling is frequent; full state/S3 counts are less frequent to avoid expensive scans. Treat resulting dashboard metrics as sampled counts, not instantaneous inventory.

## Export freshness and corruption safety

Full JSONL exporter combines a pinned historical snapshot with recent DynamoDB rows. It transforms image URLs to S3 locations, deduplicates by listing ID, emits full and sample artifacts plus metadata, uploads to S3 and may invalidate CloudFront. Use temp file -> validate gzip/JSONL/count/hash -> upload final object -> verify HEAD/checksum -> then invalidate. Historical export scripts have operator-machine file paths and explicit overwrite behavior; inspect exact command side effects before running.

A metadata file should record source snapshot key/hash, DynamoDB watermark, inclusion window, unique row count, rejected rows, image rewrite version and export timestamp. This permits consumer reconciliation and avoids silently serving a partial file as complete.
