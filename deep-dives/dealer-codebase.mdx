# Deep Dive: timoto-dealer-portal Codebase

## Repository and service shape

Root: /Users/toannguyen/timoto-dealer-portal. Django project routing is backend/timoto/urls.py. API versions overlap: current prefix /api/v1/, compatibility prefixes /api/, /api/auth/, /api/orders/ and /api/catalog/, and official VietQR callback paths. Frontend and backend live in the same repository; deployment charts and environment files choose host/service separately. Do not collapse every prefix into a single current contract.

## Domain modules

| Domain | Code | Responsibility |
| --- | --- | --- |
| auth/dealer account | backend/users | OTP signup/login, profile, store, Zalo |
| inventory/catalog | backend/catalog | Combo as dealer catalog unit; public and authenticated routers |
| order | backend/orders | Dealer order header and line items, lifecycle projections |
| auction | backend/auctions | Auctions, bids, deposit and winner transitions |
| payment | backend/payments | Deposit/full payment, checkout, VietQR, VNPay, receipts |
| bike assessment | backend/bikes | Per-bike inspection/condition assessment |
| AI report | backend/evaluations | Read AI evaluation report by bike |
| notifications | backend/notifications | Inbox and registered devices |

The Combo model in backend/catalog/models.py is a grouped inventory object with combo_id and masked_combo_id, name, brand/model/year, quantity, VND price, location, warranty/condition/colors, category, evaluation text, delivery parameters, thumbnail/media, active state, and ManyToMany bikes. ComboMedia and ComboEvaluationPart normalize media and per-condition groups. A combo is therefore not interchangeable with one physical bike ID.

## Auth flow

backend/users/urls.py declares profile, check-user, signup, confirm-signup, resend-code, login, forgot-password, verify-forgot-password-code, reset-password, deprecated confirm-forgot-password, store info/scale, and Zalo proxy/login/callback. API types in the web clients describe OTP flow: check identifier; signup sends OTP; confirm code; login step can request or verify OTP depending body; profile/store updates require an authenticated session. Confirm deprecation status from server response and consumers before removal.

Access control is server-side. Catalog may have public and private viewsets; order/payment resources must scope queryset to authenticated dealer. Never rely on frontend route guards to isolate one dealer's checkout or order.

## Catalog and assessment flow

Catalog URL routers register /api/v1/catalog/bikes/ and /public/bikes/ plus filter-options endpoints. List query accepts paging and likely brand/model/category/location filter sets as declared in serializer/viewset. Public catalog is separately routed, so document privacy fields and anonymous behavior based on PublicCatalogViewSet, not by copying the authenticated serializer. Detail response joins combo media, related bikes and evaluation parts. Similar endpoint is not listed in the backend URL output at route inspection; the v2 frontend calls /catalog/bikes/:id/similar/, so verify whether action is generated by ViewSet before treating that path as live.

Bike assessment routes use a BikeAssessmentViewSet and store normalized statuses and severity. The frontend contract exposes good/warning/error counts and ordered assessment details. Evaluation AI report is a separate GET endpoint /api/v1/evaluations/bikes/:bike_id/ai-report/. A human assessment and AI report are distinct provenance sources and should retain source/time/operator metadata.

## Orders, auction, and payment

Django root mounts orders, auctions and payments. Order body in v2 client types consists of combo_id items, delivery_location and payment_method; response has dealer_order_id/masked_order_code, item quantities/prices, total, delivery/payment status, and action booleans. Treat client types as consumer expectation, then validate serializer output before promising optional/null fields.

Auction state and payment state are not identical. An auction winner can have deposit due/paid and then full payment due/paid; a checkout ID and payment provider reference are different identifiers. Checkout API routes include create/list/detail/QR. The API may return a QR payload or checkout metadata; only verified IPN/callback changes durable payment state.

Browser return must show status but never serve as payment proof. Callback acknowledges only after validation and durable update; repeated callback should be idempotent.

## Response taxonomy from current code

The codebase uses viewset serializers and function/API views, so responses vary:

- paginated lists can emit count/next/previous/results;
- created combo/order/payment resources return serializer or custom dicts;
- auth endpoints return provider/JWT-specific bodies;
- checkout QR is not equivalent to paid;
- PDF confirmation returns application/pdf;
- VNPay return is redirect/browser content;
- callbacks return provider acknowledgement semantics.

The exact response examples must be tied to the relevant serializer or Postman fixture. Error classification: 400 validation or bad payment parameters; 401 unauthenticated; 403 dealer ownership/role; 404 unknown combo/order/checkout; 409 if provider event or state conflict is represented explicitly; 5xx upstream provider/DB errors. Do not assert a status that the handler doesn't return.

## Security and concurrency

Payment mutation needs DB transaction and idempotency around local checkout/payment row. Prevent two callbacks racing to settle one order twice. Validate provider amount equals local amount and check local currency, merchant/account identity, order reference and signature. On ambiguous timeout, read checkout state before creating another payment. Store only provider transaction identifiers needed for reconciliation and redact secrets.

Catalog/order visibility requires queryset scoping. Orders and invoices contain dealer business data; checkout detail must bind dealer user. Public catalog must suppress internal fields, private bike identifiers, acquisition price and operator notes. Auctions need race-safe bid/deposit handling; model constraints/locks should be checked around winner settlement.

## Deployment and migration notes

There are Helm/ECS/deployment scripts in the root. The existence of staging/production values is not evidence of a currently healthy service. ## Acceptance matrix

Use tests for anonymous/public catalog, dealer catalog ownership, checkout not paid until callback, valid signature, invalid signature, wrong amount, duplicate callback, callback before checkout, provider timeout after checkout create, receipt authorization, PDF content type, order action permissions, auction concurrent bids, and transaction rollback. For API docs, each row should capture method, path, auth class, query/body schema, success status/content type, error body, DB write(s), external call, idempotency key, and test name.

## Checkout response model and failure boundaries

backend/payments/checkout_views.py exposes checkout create/detail/QR operations. Model the checkout as a local state machine with a stable checkout_id, order/auction reference, amount, payment provider and status. QR response must be tied to that checkout and have a bounded validity window. A second QR request should either return/reuse active instructions or create a new provider attempt with an explicit attempt identity; never create two local paid transitions.

Keep the response types separate:

- create checkout: persisted pending checkout and provider intent/reference;
- checkout detail: canonical local status;
- QR: instructions/data only;
- VNPay return: browser-facing result/redirect;
- IPN/VietQR callback: signed settlement evidence;
- confirmation page/PDF: receipt derived from settled local row;
- delivery endpoint: fulfilment state after payment and order validations.

Each is a different contract even if UI calls them all “payment.” Error mapping should retain machine-readable provider codes while stripping credentials and raw signature. A provider timeout after checkout creation is ambiguous; GET checkout by local ID before retry.

## Callback correctness matrix

For VietQR and VNPay handlers, test all of:

1. valid signature, exact amount/order, first delivery -> one payment transition;
2. same callback repeated -> same durable result or documented duplicate acknowledgement;
3. wrong amount/currency/order/merchant -> reject and do not set paid;
4. invalid or missing signature -> reject before business mutation;
5. callback before local row or unknown order -> safe error and operator reconciliation;
6. race between two identical callbacks -> one settlement row/update;
7. malformed payload or provider outage -> bounded response with no false paid state;
8. browser return arrives before IPN -> show pending/processing and refresh canonical order.

The source route mount includes both versioned and legacy /api/payments/; run identical tests through each mount and compare policy. The official bank callback paths at /bank/api/transaction-sync may have a distinct payload and auth contract; do not alias assumptions across providers.

## Order action flags

V2 TypeScript response has can_cancel, can_receive, can_pay, can_get_invoice and can_reorder. These booleans are UX hints. The backend must recalculate legality at mutation time under a transaction; order state can change between list read and button click. A disabled button is not authorization. Contract tests should send forbidden commands directly and assert no change to order or payment rows.

## Data lineage

Combo is the catalog aggregate; Order is the dealer transaction aggregate; checkout is the payment attempt; auction is the competitive allocation; bike is the physical item. Preserve the join keys separately. A buyer order referencing combo_id should snapshot price/name/media at purchase time or otherwise define how catalog edits affect active orders. That answer must be proven from order create code/model before documenting repricing behavior.
