## Summary

This is the prompt you paste into Cursor when the KB is still too thin. The failure mode last time was **screen maps without contracts**. This prompt forces three sources on every hop: **Postman saved 200 body**, **git spec (TMA / IA / CONTRACT)**, **Django model \+ FE widget**.

## Prompt (copy this)

```text
You are expanding the private TiMoto Mintlify KB (deployment timoto-ai, English).

## Sources — read in this order, do not skip
1. SPECS IN GIT (the product already wrote the flow — quote them):
   - timoto-internal-app/docs/API_LISTING_FLOW.md (TMA-79 listing vs instant)
   - timoto-internal-app/docs/FE_FMP_TIPP_DUAL_PRICE.md (OPS types FMP only)
   - timoto-internal-app/docs/API_OPERATOR_OFFER_DUAL_PRICE.md (HMAC body)
   - timoto-mobile/docs/pr/TMA-PICKUP-RESCHEDULE_DESIGN_SPEC.md (TMA-168)
   - timoto-dealer-portal/docs/api/SHARED_CHECKOUT_CONTRACT.md
   - timoto_dealer_portal_v2/docs/CONTRACT.md
   If Word/Figma is missing, say MISSING and still implement from these files.
2. POSTMAN (copy every request + every saved example, especially 200/201/400/409):
   - timoto-mobile/backend/postman/Timoto_API.postman_collection.json
   - timoto-internal-app/docs/postman/TiMoto-Internal-API.postman_collection.json
   - timoto-dealer-portal/backend/TiMoto_Dealer_Portal_API.postman_collection.json
   Redact tokens/HMAC secrets. Keep field names and numeric examples.
3. CODE OF TRUTH for anything newer than Postman:
   - urls.py / api_urls.py / Apps/src/api/endpoints.ts / dealer FE apiClient
   List APIs that exist in code but NOT in Postman (purchase-orders, listing/confirm, dealer-order/create, media/batch).
4. DATABASE: the model class, table, fields written on 200, fields the FE actually reads.

## Page types you must produce
A. Feature page (one product behavior): why it exists, who types what, formulas, invariants.
B. Flow page (one user journey): screen → method+path → request JSON → 200 JSON → which keys the screen binds → next screen → error toast.
C. API catalog page: Postman dump with request + 200 (+ 400/409 if saved).

## Required block for EVERY hop (no hop without this)
### Hop: <screen or job> → <METHOD path>
- Why this call exists (one sentence of reasoning, from spec).
- Caller: file + function.
- Auth: JWT / HMAC / AllowAny.
- Request JSON (full).
- 200 JSON (full, from Postman or serializer test — never invent fields).
- Other statuses the FE handles (404 login, 409 pickup completed, 422 FMP).
- DB write: table.column (e.g. pricing_entries.offer_to_user, bikes.marketplace_status).
- DB read: who else consumes it (HMAC operator-offer, sale-history card).
- Frontend: widget + copy (VI) + which JSON key. If the spec shows a field the UI does not render, mark SPEC GAP.
- Next screen on 200 / on failure.

## Reasoning rules
- If spec and UI disagree, document BOTH and say which is live code.
- If Postman 200 includes unused keys (evaluation_id, valuation_price on health), say “legacy envelope — FE ignores”.
- Never tell FE to POST listing_price_vnd / instant_price_vnd to OPS.
- Never put HMAC secrets in the app binary or in Mintlify.
- Do not pad to a line quota. Completeness = every hop has the block above.

Ship via Mintlify Admin MCP. Site stays Private. Cite slugs for Autonoma.
```

## What “done” looks like

You can answer without grepping: “OPS types 25M FMP — what does the seller see, which table stored it, which GET returns it, which button POSTs `option: listing`?” If any of those four is missing, the page is still too thin.
