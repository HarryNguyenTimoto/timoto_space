## Scope

TiMoto has six application/data repositories and one incident-repair control plane. The six application repositories are mobile, internal operations, dealer backend, dealer SPA, public landing, and Chotot data. The seventh project is AI_infra_timoto.

This page is the compact map. The [Seven-project specification](/architecture/seven-project-spec) is the source-grounded contract and verification record.

## Repository ownership matrix

| Project | Host / execution | Primary responsibility | Data boundary |
| --- | --- | --- | --- |
| timoto-mobile | api.timoto.ai; ECS/Fargate backend | Rider auth, bike/media/evaluation, pickup, listing and marketplace | Owns rider-facing TMA rows and media references; consumes Cognito and AI service. |
| timoto-internal-app | internal.timoto.ai; web/RN plus Django/workers | Operator review, FMP/TIPP snapshot, pickup, inspection, payout and completion | Own operational DB plus explicit tma_db and user_db_write aliases; mirrors do not own TMA tables. |
| timoto-dealer-portal | dealer.timoto.ai; Django/ECS | Catalog, dealer orders, auctions, VietQR, evaluation read and notifications | Owns dealer/catalog/payment state; uses S2S and HMAC boundaries to mobile/internal. |
| timoto_dealer_portal_v2 | dealer browser SPA; nginx/ECS | Dealer auth, catalog, orders, auctions and payments UI | No database owner; build-time VITE API base and Axios are client configuration. |
| TiMoto-AI-Web | timoto.ai; Vite static deployment | Public marketing landing and App Store/download CTAs | No evaluation or transaction writer. Current Android waitlist submit is UI-only. |
| chototcaodulieu | Lambda/EC2, DynamoDB/S3, CloudFront | Chotot scrape, refresh, image sync, quality export and dashboard | Research dataset only; no documented Aurora write. |
| AI_infra_timoto | Singapore control plane; ECS/Lambda/S3/DynamoDB | Evidence intake, bounded repair/test, verifier, draft PR and read-only console | Incident state/evidence only; no business-row ownership and no merge/deploy authority. |

## Data boundaries

- Mobile and Internal interact through explicit webhooks, HMAC operator-offer reads, PostgreSQL notification channels, and worker/outbox state.
- Dealer reads/writes its own order/catalog/payment models and receives mobile inventory events through an allowlisted S2S contract.
- The public landing is not the gRPC evaluation service. A VITE API value is not evidence that the browser made a request.
- Chotot DynamoDB and S3 exports stay isolated until a separately approved ETL/pricing contract exists.
- AI infrastructure sees sanitized incident evidence and immutable source manifests, not raw credentials or unbounded customer data.

## Integration flow

1. Mobile creates a bike and requests asynchronous evaluation.
2. The mobile backend calls the separate gRPC AI service and notifies Internal through HMAC/webhook and PostgreSQL notification paths.
3. Internal submits FMP and the server snapshots listing and instant prices.
4. Mobile shows the operator-approved snapshot; the seller chooses listing or instant flow.
5. Dealer consumes eligible inventory through catalog/auction/checkout contracts.
6. VietQR and payout callbacks update the owning service, then send an allowlisted HMAC event across the boundary.
7. CloudWatch observations enter AI_infra_timoto. The control plane can prepare a signed draft PR; a human owns merge, deploy and rollback.

## Do not infer

- A running ECS task is not proof of API health.
- A Jira key, PR URL or HTTP 200 is not proof that the external action completed correctly.
- A source README is not proof of the deployed image or task definition.
- Dealer EKS/ALB references and newer ECS/NLB references must be reconciled against live AWS before deployment.
- Waitlist Lambda documentation is not proof that the current landing form is wired to it.
